# Техническое задание и требования
## Информационная система «Продуктовый интернет-магазин»

*Автор раздела: Студент 1 (Системный аналитик)*

## 1. Наименование системы
Информационная система «Продуктовый интернет-магазин».

## 2. Назначение
Автоматизация продажи продуктов питания через интернет: клиент самостоятельно выбирает товары, оформляет и оплачивает заказ с доставкой, а сотрудники магазина управляют каталогом и обработкой заказов.

**Цель системы:** сократить время обслуживания клиента, исключить ошибки ручного приёма заказов и обеспечить прозрачный учёт остатков и статусов доставки.

## 3. Пользователи системы
| Роль | Описание | Основные действия |
|---|---|---|
| Клиент | Покупатель | Регистрация, каталог, поиск, корзина, заказ, оплата, отслеживание |
| Администратор | Сотрудник магазина | Управление каталогом, просмотр всех заказов, смена статусов |
| Курьер | Сотрудник доставки | Смена статусов «В доставке» / «Доставлен» |
| Платёжная система | Внешняя система | Проведение платежа (карта, СБП) |

| ID | Бизнес-требование | Приоритет | Use Case | Класс / сервис |
|---|---|---|---|---|

| BR-02 | Просмотр каталога продуктов по категориям (овощи, молочные продукты, бакалея и т.д.) | Высокий | Просмотр каталога | `Product`, `CatalogService` |

| BR-04 | Добавление продуктов в корзину, изменение количества/веса | Высокий | Добавление в корзину | `Cart`, `CartItem`, `CartService` |
| BR-05 | Оформление заказа с указанием адреса и времени доставки | Высокий | Оформление заказа | `Order`, `OrderItem`, `OrderService.checkout` |

## 5. Функциональные требования
| ID | Требование |
|---|---|
| ФТ-01 | Регистрация по имени, email и паролю (пароль ≥ 6 символов, email уникален) |
| ФТ-02 | Вход по email и паролю; роли: клиент, администратор, курьер |
| ФТ-03 | Каталог с группировкой по категориям; у товара есть название, описание, цена, остаток, единица измерения (шт/кг) |
| ФТ-04 | Поиск по части названия (без учёта регистра) и фильтр по диапазону цен |
| ФТ-05 | Корзина: добавить товар, изменить количество/вес, удалить позицию, показать итоговую сумму |
| ФТ-06 | Оформление заказа: обязательны адрес и время доставки; заказ не создаётся при пустой корзине |
| ФТ-07 | При оформлении проверяется наличие товара на складе (`<<include>>`); при нехватке выдаётся сообщение |
| ФТ-08 | Расчёт стоимости (`<<include>>`): сумма позиций + доставка (200 ₽/сом; бесплатно от 1500) |
| ФТ-09 | Оплата: банковская карта, наличные, СБП; при неуспехе оплату можно повторить |
| ФТ-10 | Статусы заказа: Новый → Оплачен → Собирается → В доставке → Доставлен; отмена до сборки |
| ФТ-11 | Клиент видит историю своих заказов и текущие статусы; администратор — все заказы |
| ФТ-12 | Администратор добавляет товары, меняет цены, списывает остатки |
| ФТ-13 | Менять статус заказа может только администратор или курьер; недопустимые переходы запрещены |

## 6. Нефункциональные требования
| ID | Категория | Требование |
|---|---|---|
| НФТ-01 | Производительность | Время отклика при поиске — не более 2 секунд |
| НФТ-02 | Безопасность | Пароли хранятся только в виде соленого хэша (PBKDF2-SHA256); персональные данные доступны только владельцу и администратору |
| НФТ-03 | Надёжность | История заказов и содержимое корзины сохраняются при перезагрузке системы |
| НФТ-04 | Многопользовательность | Одновременная работа нескольких клиентов без потери данных; остатки списываются при оформлении |
| НФТ-05 | Удобство | Понятный интерфейс: оформление заказа не более чем за 5 шагов |
| НФТ-06 | Расширяемость | Новый способ оплаты добавляется без изменения существующего кода (принцип OCP) |

## 7. Основные сущности
`User`, `Product`, `Cart`, `CartItem`, `Order`, `OrderItem`, `Payment` — подробно в [Entities.md](Entities.md).

## 8. Внешние системы
Платёжная система (банк-эквайер, СБП) — в учебной версии эмулируется классами `CardPayment`, `SBPPayment`.

## 9. Архитектурные требования
- разделение ответственности (сервисы, репозитории, модели);
- использование интерфейсов (`IPayment`, `IProductReader`, …);
- слабая связанность: зависимости внедряются через конструктор;
- расширяемость и применение принципов SOLID — см. [SOLID.md](SOLID.md).

## 10. Ограничения учебной версии
Хранилище — в памяти (in-memory), без веб-интерфейса и реальных платёжных шлюзов. Архитектура допускает замену репозиториев на БД без изменения сервисов.
